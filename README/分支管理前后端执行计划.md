# 分支管理前后端执行计划

## 1. 目标

让 `PROJECT_ADMIN` 可以直接在 Qgents 中管理项目仓库的远程分支，解决自动建仓后只有 `main`、用户无法在平台创建 `develop` 的问题。

本功能的核心目标是：

```text
项目管理员进入项目仓库
  -> 查看 GitHub 远程分支
  -> 从已有分支或提交创建 develop
  -> 将项目使用的默认基准分支设置为 develop
  -> 后续 Task / Workspace / Dry Run / MR 自动沿用 develop
```

本功能不重写现有 Task、Workspace、Sandbox、Dry Run、CQ+1 和 MR 流程；这些流程继续消费已经存在的 `baseRef/defaultBranch/targetBranch` 字段。前端不新建独立的“分支管理”页面，优先复用现有项目详情的“代码与 Branch”入口和仓库设置区域。

## 2. 产品决策

### 2.1 项目默认分支与 GitHub 默认分支分离

Qgents 中设置的 `defaultBranch` 是“该项目使用的默认基准分支”，不是强制修改 GitHub 仓库在 GitHub 页面上的全局默认分支。

原因：同一个 GitHub 仓库可能被多个 Qgents 项目绑定，不同项目可以分别使用 `main` 或 `develop`。修改 GitHub 全局默认分支会影响项目外的用户和其他项目，风险较大。

因此本计划采用：

- GitHub 仓库的真实默认分支继续由 GitHub 管理；
- Qgents 项目管理员可以设置本项目绑定使用的默认基准分支；
- Task 显式 `baseRef` 优先于项目默认分支；
- 未传 `baseRef` 的 Task 使用项目仓库绑定的 `defaultBranch`；
- `defaultBranch` 必须是 GitHub 上真实存在的分支。

### 2.2 首期功能范围

首期实现：

- 查询项目仓库的远程分支列表；
- 从已有分支或提交创建远程分支；
- 设置项目默认基准分支；
- 创建前和设置前校验分支真实存在；
- 返回分支 SHA、是否项目默认分支和可操作状态；
- Web 前端管理员操作页面；
- 移动端复用同一接口展示和设置默认分支。

暂不实现：

- 修改 GitHub 仓库全局默认分支；
- 任意 Git 命令终端；
- 分支重命名；
- 强制删除受保护分支；
- 分支合并；分支合并继续通过 MR 完成；
- 让普通项目成员创建或删除远程分支。

删除远程分支可作为第二阶段能力，必须完成保护校验后再开放。

## 3. 现有代码复用点与缺口

### 3.1 已有能力

- `GitHubAppClient.getBranch(...)` 已能查询单个远程分支及其 commit SHA；
- `GitHubRepositoryController` 已有项目仓库查询、绑定、解绑和 `PATCH` 更新默认分支接口；
- `UpdateProjectRepositoryRequest.defaultBranch` 已存在；
- `ProjectRepositoryEntity.defaultBranch` 已持久化；
- `TaskCreateRequest.baseRef` 和 `TaskTriggerRequest.baseRef` 已支持任务级基线分支；
- `SandboxSessionManager` 已优先使用 Workspace `baseRef`，再回退项目仓库 `defaultBranch`；
- `TestRunService`、`PreflightGateService`、`MrFirstAutomationService` 已按目标分支执行 Dry Run、Testset 和 MR 预检；
- `RepositoryBranchConfigController` 已支持按分支配置 Branch Policy 和 Quality Gate。

前端已经存在以下实现：

- 路由 `/app/projects/{projectId}/code`；
- `CodePage.tsx` 的“分支/MR”双 Tab；
- `githubApi.workBranches()` 和 `useWorkBranches()`；
- `GET /api/v1/projects/{projectId}/work-branches` 的真实工作分支列表；
- 按仓库卡片展示工作分支、关联 Task、Diff、MR 和最近验证；
- 需求群过滤和 Branch 详情 Drawer；
- 项目设置页已展示绑定仓库和当前 `defaultBranch`；
- `githubApi.updateProjectRepository()` 已有 PATCH 封装，但当前 payload 只允许 `displayName`，并明确不调用修改默认分支。

### 3.2 当前缺口

- 没有查询 GitHub 全部远程分支的接口；现有 `work-branches` 只返回 Qgents Task/Workspace 工作分支，不是远程分支管理数据；
- 没有创建远程分支接口；
- `GitHubAppClient` 没有 create ref / delete ref 方法；
- 设置项目默认分支前没有调用 GitHub 校验分支存在；
- 前端已有 Branch 入口，但当前页面是只读的工作分支视图，没有远程分支创建和默认分支设置操作；
- 接口文档 §6 明确写着“第一版前端不提供修改默认分支入口”，需要更新；
- 前端已有的 `ProjectBranchRow`/演示分支模型不能直接替代远程分支 DTO；远程分支和工作分支需要在类型和 API 层分开。

## 4. 目标分支选择逻辑

最终规则固定为：

```text
Task.baseRef（显式指定）
  -> WorkspaceRepository.baseRef（任务创建时固化）
  -> ProjectRepository.defaultBranch（项目默认）
  -> GitHubRepository.defaultBranch（仅作为绑定时的初始值）
```

任务创建后，实际使用的基准分支必须固化到 Workspace worktree 的 `baseRef`。后续 Worker、Dry Run、CQ+1 和 MR 都使用这一个值，不在执行中再次根据当前项目默认值漂移。

示例：

```text
项目默认分支：develop
Task 未传 baseRef
Workspace.baseRef：develop
Task 工作分支：feat/task-xxx
Dry Run targetBranch：develop
MR targetBranch：develop
```

如果项目默认分支已经从 `main` 改为 `develop`，旧 Task/Workspace 不自动切换，避免历史任务的基线事实被改变；只有新建 Task 或显式传入 `baseRef=develop` 的任务使用新分支。

## 5. 后端执行计划

### 阶段 A：定义接口和权限（P0）

涉及模块：

- `GitHubRepositoryController`
- `GitHubRepositoryService`
- `GitHubAppClient`
- `RestGitHubAppClient`
- 分支 DTO 与异常映射

权限规则：

- 查询远程分支：项目成员；
- 创建远程分支：`PROJECT_ADMIN`；
- 设置项目默认分支：`PROJECT_ADMIN`；
- 删除远程分支：首期不开放；后续仍仅 `PROJECT_ADMIN`；
- 所有操作先校验 `projectRepositoryId` 属于当前项目且绑定状态为 `ACTIVE`。

不得信任客户端传入的 `userId`、`projectId` 归属、管理员标记或 GitHub provider ID。

### 阶段 B：远程分支查询（P0）

新增接口。该接口服务于现有 `CodePage` 的“远程分支管理”能力，不替换已有 `work-branches` 接口：

```http
GET /api/v1/projects/{projectId}/repositories/{projectRepositoryId}/branches
```

查询参数建议：

|参数|说明|
|---|---|
|`keyword`|按分支名过滤，可选|
|`cursor`|分页游标，可选|
|`limit`|默认 50，最大 100|
|`includeSha`|是否返回最新 commit SHA，默认 true|

响应字段：

```json
{
  "data": [
    {
      "name": "main",
      "headCommit": "40位SHA",
      "isProjectDefault": false,
      "isGithubDefault": true,
      "canCreateTaskFrom": true,
      "canDelete": false
    },
    {
      "name": "develop",
      "headCommit": "40位SHA",
      "isProjectDefault": true,
      "isGithubDefault": false,
      "canCreateTaskFrom": true,
      "canDelete": false
    }
  ],
  "page": {"nextCursor": null}
}
```

实现要求：

1. 通过 GitHub App 受控调用查询，不向客户端返回凭证；
2. 不把 GitHub 分支列表永久缓存为本地事实，必要时短时缓存，创建 Task/Dry Run 前仍以实时校验为准；
3. GitHub 404 映射为 `GIT_BRANCH_NOT_FOUND`；
4. GitHub 暂时不可用映射为 `GITHUB_API_UNAVAILABLE`；
5. 分支名和 SHA 必须由 GitHub 返回，不能由本地字符串推断。

### 阶段 C：创建远程分支（P0）

新增接口：

```http
POST /api/v1/projects/{projectId}/repositories/{projectRepositoryId}/branches
Idempotency-Key: <stable-key>
```

请求体：

```json
{
  "name": "develop",
  "fromRef": "main"
}
```

字段规则：

- `name` 必填，限制为合法 Git 分支名；禁止 `refs/heads/` 前缀、空白、`..`、`//`、`.lock` 结尾和 commit SHA 伪装值；
- `fromRef` 必填，可为已存在分支名或完整 commit SHA；
- 客户端不能传 GitHub Token、provider installation ID、provider repository ID 或目标 SHA；
- 服务端先解析 `fromRef` 为真实 SHA，再调用 GitHub 创建 ref；
- 创建操作必须使用幂等键，重复请求返回已存在分支或稳定冲突，不重复创建。

后端调用链：

```text
校验项目管理员和仓库归属
  -> 校验 name
  -> GitHub 查询 fromRef
  -> 调用 GitHub POST /repos/{owner}/{repo}/git/refs
  -> 校验返回 ref 和 object SHA
  -> 发布 branch.updated
  -> 返回分支摘要
```

GitHub App 必须具备目标仓库的 Contents 写权限。不能把 GitHub 长期 Token 交给前端或 Agent。

建议错误码：

|错误码|含义|HTTP|
|---|---|---|
|`PROJECT_REPOSITORY_NOT_FOUND`|仓库绑定不属于当前项目|404|
|`PROJECT_ADMIN_REQUIRED`|无项目管理员权限|403|
|`INVALID_BRANCH_NAME`|分支名不合法|400|
|`GIT_BRANCH_NOT_FOUND`|来源分支不存在|404|
|`GIT_BRANCH_ALREADY_EXISTS`|目标分支已存在|409|
|`GITHUB_BRANCH_CREATE_FORBIDDEN`|GitHub App 无写权限|403|
|`GITHUB_API_UNAVAILABLE`|GitHub 暂时不可用|502/503|
|`BRANCH_CREATE_CONTEXT_STALE`|来源分支在操作期间发生变化|409|

### 阶段 D：设置项目默认基准分支（P0）

复用现有接口：

```http
PATCH /api/v1/projects/{projectId}/repositories/{projectRepositoryId}
```

请求：

```json
{
  "defaultBranch": "develop",
  "displayName": "backend"
}
```

需要修改 `GitHubRepositoryService.updateProjectRepository()`：

1. 校验分支名格式；
2. 调用 GitHub 查询分支，确认真实存在；
3. 确认仓库未归档、GitHub App 安装仍为 ACTIVE；
4. 在短事务内更新 `project_repositories.default_branch`；
5. 发布 `project-repository.updated` 或 `branch.updated`，payload 只带项目仓库 ID、分支名和时间；
6. 不修改 GitHub 仓库全局默认分支；
7. 不修改已有 Workspace 的 `baseRef`，避免历史任务漂移。

如果 GitHub 查询成功但数据库更新失败，不应向前端返回成功；如果数据库更新成功后事件发布失败，使用事务后事件或补偿扫描恢复通知。

### 阶段 E：可选删除远程分支（P1）

首期可以不开放删除，先保证创建 `develop` 的核心场景。后续开放时新增：

```http
DELETE /api/v1/projects/{projectId}/repositories/{projectRepositoryId}/branches/{branchName}
Idempotency-Key: <stable-key>
```

删除前必须检查：

- 不是 GitHub 默认分支；
- 不是 Qgents 项目默认分支；
- 没有 OPEN/REOPENED 或 CLOSED 未合并 MR；
- 没有活动 Workspace 将其作为 `baseRef`；
- 没有正在运行的 Dry Run/TestRun 依赖该分支；
- 删除操作由 GitHub 返回真实成功后才落本地审计事件。

删除不应删除 Qgents 的历史 Task、Workspace、Diff、TaskRun 或 MR 记录；历史事实保持可查询。

### 阶段 F：与现有执行链路接通（P0）

不改变核心编排流程，只补校验和展示：

```text
项目管理员创建 develop
  -> 设置 project_repositories.default_branch=develop
  -> 新 Task 未传 baseRef
  -> WorkspaceRepository.baseRef 固化为 develop
  -> Sandbox 同步 develop
  -> Dry Run targetBranch=develop
  -> 读取 develop 的 Testset/Quality Gate
  -> MR targetBranch=develop
```

必须补充回归测试确认：

- `baseRef=develop` 不会被项目默认 `main` 覆盖；
- 项目默认 `develop` 不会被 GitHub 全局默认 `main` 覆盖；
- `develop` 不存在时设置默认分支立即失败，不等到 Worker 启动才失败；
- 目标分支刷新和 Dry Run 使用同一个 `develop`；
- 多仓库任务允许每个仓库使用各自项目绑定的默认分支；
- 历史 Workspace 的 `baseRef` 不随项目默认分支修改而变化；
- MR 创建时使用 Workspace 固化的 target branch。

## 6. 数据库计划

首期不新增数据库表或字段，复用：

- `project_repositories.default_branch`：项目级默认基准分支；
- `workspace_repositories.base_ref`：Task Workspace 实际固化的基准分支；
- `workspace_repositories.base_commit`：实际解析后的基线 SHA；
- `dry_runs.target_branch/resolved_target_commit`：Dry Run 固化上下文；
- `merge_requests.target_branch`：真实 MR 目标分支。

如需要审计分支创建/删除，再新增独立的 `project_branch_operations` 表或复用统一事件日志，不能把远程分支伪造为 Task/TaskRun 产物。

如果新增表，必须同时更新：

- `src/main/resources/db/qgents_schema.sql`；
- 独立版本化 Flyway migration；
- Entity、Mapper、Service、DTO 和接口文档。

## 7. GitHub 接口实现计划

### 7.1 GitHub 客户端新增方法

在 `GitHubAppClient` 增加受控方法：

```java
GitHubBranchDetails getBranch(...);
GitHubBranchDetails createBranch(..., String branchName, String sourceSha);
void deleteBranch(..., String branchName);
```

`RestGitHubAppClient` 负责：

- 调用 GitHub REST API；
- 处理 404/409/422/403/429/5xx；
- 不记录访问令牌和完整响应中的敏感字段；
- 对返回的 ref、branch name 和 SHA 做一致性校验；
- 为网络错误保留稳定错误码。

### 7.2 权限与凭证

- 使用现有 GitHub App 安装身份；
- GitHub App 需要对目标仓库具备 Contents: Read and write；
- 前端只发送分支名和来源引用，不发送 Token；
- Agent 不直接调用分支管理接口；
- 每个调用都按 Project、ProjectRepository 和 Installation 归属校验。

## 8. Web 前端执行计划

### 8.0 现有页面复用原则

不要新增一个与“代码与 Branch”并列的分支页面。当前页面已经承担两种不同信息：

|现有/新增区域|数据来源|用途|
|---|---|---|
|工作分支表格|`GET /projects/{projectId}/work-branches`|查看 Task/Workspace 开发状态、Diff、MR 和验证结果|
|远程分支管理|新增 `GET /projects/{projectId}/repositories/{projectRepositoryId}/branches`|查看 GitHub 真实分支、创建 `develop`、选择项目默认基准|
|仓库默认配置|已有 `PATCH /projects/{projectId}/repositories/{projectRepositoryId}`|设置当前项目的 `defaultBranch`|

两者不能合并成一个 DTO：

- 工作分支有 `workspaceId/latestTask/latestDiff/openMergeRequest`；
- 远程分支有 `headCommit/isGithubDefault/isProjectDefault`；
- `main/develop` 可能没有 Task/Workspace；
- `feat/task-*` 既是远程分支，也可能出现在工作分支视图，但两者的状态语义不同。

### 8.1 页面入口

复用 `CodePage.tsx` 的现有“代码与 Branch”页面：

1. 保留现有“工作分支”表格和需求群过滤，不改其 `work-branches` 数据契约；
2. 每个仓库卡片增加“远程分支”折叠区或管理按钮；
3. 远程分支区消费新增分支列表接口；
4. 仅对 `PROJECT_ADMIN` 显示“创建分支”和“设为项目默认”操作，普通成员只读；
5. 项目设置页的绑定仓库卡片增加“修改项目默认分支”入口，或由 CodePage 的远程分支区统一操作，二者只保留一个写入口。

列表展示：

- 分支名；
- 最新提交短 SHA；
- 是否 GitHub 默认分支；
- 是否 Qgents 项目默认基准分支；
- 创建任务入口；
- 分支门禁配置入口。

### 8.2 创建分支交互

表单：

- 分支名；
- 来源分支下拉框或来源提交引用；
- 创建按钮；
- 明确提示“创建的是远程 GitHub 分支”。

交互规则：

- 提交时生成稳定 `Idempotency-Key`；
- 请求中显示处理中，禁止重复点击；
- 成功后刷新分支列表；
- `GIT_BRANCH_ALREADY_EXISTS` 直接提示“分支已存在”，并刷新列表；
- GitHub 不可用时显示重试，不显示为任务失败；
- 创建分支后可直接点击“设为项目默认基准分支”。

### 8.3 设置默认分支交互

- 仅项目管理员可见；
- 二次确认，提示会影响后续新建 Task/Dry Run/MR；
- 明确提示不会修改已有 Task/Workspace，也不会修改 GitHub 全局默认分支；
- 后端返回成功后再更新本地状态；
- 收到 `branch.updated` 或 `project-repository.updated` 后重新 GET 项目仓库和分支列表。

### 8.4 API 与类型改动

前端具体修改点：

- `src/api/github.ts` 增加 `listRemoteBranches()` 和 `createRemoteBranch()`；
- 扩展 `updateProjectRepository()` 的 payload，允许 `defaultBranch`，但不能让调用方传 provider ID 或 SHA；
- `src/types/github.ts` 增加 `RemoteBranch`、`CreateRemoteBranchPayload`；
- `src/query/queryKeys.ts` 增加按项目仓库维度的远程分支 key；
- `CodePage.tsx` 复用现有仓库卡片，新增远程分支区和操作 Drawer/Modal；
- `SettingsPage.tsx` 只增加入口或刷新联动，不复制分支列表；
- 删除/废弃 `ProjectBranchRow` 中仅用于演示的远程分支字段前，先确认是否仍被 Diff 演示页使用，避免无关重构；
- Mock handler 必须与真实 API 使用同一 `githubApi` 调用链，不在组件内直接读取 fixture。

### 8.5 任务创建联动

- 任务创建页显示可用远程分支；
- 默认选中项目默认分支；
- 用户可以为当前任务选择其他已有分支，提交 `baseRef`；
- 不允许把不存在的分支提交到 Task API；
- 从群里直接 `@AI` 且未指定基线时，使用项目默认分支；
- 分支选择不改变群与分支的隔离关系，Requirement Group 仍是聊天上下文边界。

## 9. 移动端执行计划

移动端复用相同接口和后端权限，不复制分支规则：

- 项目仓库详情增加分支列表；
- Project Admin 可创建分支、设置项目默认分支；
- 普通成员只读查看；
- 任务发布页可选择已有基准分支；
- 创建成功、已存在、无权限、分支不存在和 GitHub 不可用分别展示；
- SSE 断线后重新拉取分支列表和项目仓库详情；
- 不在客户端自行判断分支是否存在或拼接 GitHub API。

## 10. SSE 与事件

新增或复用事件：

```text
branch.updated
project-repository.updated
```

事件 payload 建议：

```json
{
  "projectId": "project-uuid",
  "projectRepositoryId": "project-repository-uuid",
  "branchName": "develop",
  "headCommit": "sha",
  "isProjectDefault": true,
  "operation": "CREATED|DEFAULT_CHANGED|DELETED",
  "timestamp": "2026-08-19T12:00:00Z"
}
```

事件只用于刷新提示，不作为完整事实来源。前端收到事件后重新调用分支列表和项目仓库详情。

## 11. 接口文档修改范围

以 `Qgents 接口文档v2.0.12.md` 为基线，修改以下内容：

1. **§6 GitHub App 与项目仓库**

## 12. 测试计划

### 12.1 后端 Service 测试

- 非项目成员不能读取项目分支；
- 非 Project Admin 不能创建分支或设置默认分支；
- 跨项目 `projectRepositoryId` 返回 404；
- 来源分支不存在时不调用创建 ref；
- 非法分支名全部被拒绝；
- 已存在分支返回稳定 409；
- 创建分支返回真实分支名和 SHA；
- 同一幂等键重复请求只创建一次；
- 设置默认分支前校验远程分支存在；
- 设置默认分支失败时数据库不发生错误更新；
- 修改项目默认分支不改动旧 Workspace `baseRef`；
- GitHub 403/404/409/422/5xx 映射稳定错误码。

### 12.2 GitHub 客户端测试

- create ref 请求路径、body 和分支名正确；
- 返回 ref 与 object SHA 不一致时失败；
- GitHub 返回 422 映射 `GIT_BRANCH_ALREADY_EXISTS` 或明确的创建失败码；
- 不在日志中输出 Token；
- 超时和限流可重试但不会重复创建。

### 12.3 回归测试

- 未传 `baseRef` 的新 Task 使用项目默认 `develop`；
- 显式 `baseRef=main` 覆盖项目默认 `develop`；
- Dry Run、CQ+1 和 MR 都使用同一 Workspace `baseRef`；
- `develop` 未配置 Testset 时返回 `NOT_REQUIRED`，不会错误加载 `main` 的 Testset；
- 多仓库项目可分别使用各自绑定的默认分支；
- 已有 MR 的 Task 工作分支仍受原有锁定逻辑保护；
- 创建管理员分支不会被误认为 Task 工作分支或用户 Diff。

### 12.4 前端测试

- 管理员和普通成员看到的操作权限不同；
- 创建分支按钮防重复点击；
- 创建成功后列表和默认标识刷新；
- 设置默认分支二次确认和失败回滚；
- SSE 重复、乱序、断线后重新拉取；
- 分支不存在、已存在、无权限、GitHub 故障提示正确；
- 任务创建页只允许选择后端返回的已有分支。

## 14. 验收标准

- 管理员可以在 Qgents 中看到项目仓库的 `main`；
- 管理员可以从 `main` 创建 `develop`；
- 管理员可以将项目默认基准分支设置为 `develop`；
- 新任务未传 `baseRef` 时使用 `develop`；
- 旧任务仍保持原来的 `baseRef`；
- Dry Run、Testset、CQ+1 和 MR 目标分支均为 `develop`；
- 分支不存在、权限不足、重复创建和 GitHub 故障都有明确错误；
- 普通成员不能创建分支或修改默认分支；
- 前端不接触 GitHub 凭证；
- 没有新增 Deliverable、TaskRunStep 或独立 Diff/MR 模型；
- 不修改 GitHub 全局默认分支，不影响项目外用户；
- 现有 Task、Workspace、MR 锁定和 Dry Run 流程回归通过。
